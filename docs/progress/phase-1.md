# Phase 1: Database and data layer

Completed 2026-11-16. Not committed; Adam commits.

## What was built

- **Schema** in `lib/db/schema.ts` (Drizzle ORM): the four tables from the plan's "Data model", with the same columns, foreign keys (`ON DELETE CASCADE` / `RESTRICT`), unique constraints, check constraints and the unique index on `lower(name)`.
- **First migration** `drizzle/0000_init.sql`, generated by drizzle-kit, plus its bookkeeping files in `drizzle/meta/`. All of `drizzle/` is meant to be committed.
- **Database client** `lib/db/client.ts`: one `pg` connection pool wrapped by Drizzle, reading `DATABASE_URL`.
- **Scripts**: `db:generate`, `db:migrate`, `db:seed` (`scripts/seed.ts`: five exercises and three workouts in the last week).
- **Query functions** in `lib/db/queries/`:

  | File | Functions |
  | --- | --- |
  | `exercises.ts` | `searchExercises`, `createExercise`, `renameExercise`, `archiveExercise`, `unarchiveExercise`, `deleteExercise` |
  | `workouts.ts` | `getWorkoutByDate`, `getOrCreateWorkout`, `updateWorkoutNotes`, `deleteWorkout`, `listWorkoutSummaries` |
  | `workout-exercises.ts` | `addExerciseToWorkout`, `removeWorkoutExercise`, `reorderWorkoutExercises` |
  | `sets.ts` | `addSet`, `updateSet`, `deleteSet`, `getLastSessionSets` |

- **Errors** in `lib/db/errors.ts`: `NotFoundError`, `ExerciseNameTakenError`, `ExerciseInUseError`, and `pgErrorCode()` for reading Postgres error codes.
- **Metrics** in `lib/metrics/sets.ts` (pure functions): `setVolume`, `sessionVolume`, `estimatedOneRepMax`, `bestSet`.
- **Zod schemas** in `lib/validation/schemas.ts`: `exerciseNameSchema`, `repsSchema`, `weightKgSchema`, `setInputSchema`.

## Decisions and deviations

- **Drizzle 0.45 (stable), not 1.0.** The Drizzle docs now show install commands with the `@rc` tag (1.0 release candidate); npm's `latest` is still `drizzle-orm` 0.45.4 / `drizzle-kit` 0.31.11, and that is what is installed. Moving to 1.0 once it is released is a separate, later step.
- **Driver: `pg` (node-postgres).** It works unchanged against Docker Postgres and Neon. Phase 2 should use Neon's *pooled* connection string for the app on Vercel.
- **New dependencies:** `drizzle-orm`, `pg`, `zod` (runtime); `drizzle-kit`, `@types/pg`, `tsx` (dev). `tsx` runs `scripts/seed.ts`, which needs the `@/` import alias. No `dotenv`: `.env.local` is loaded with Node's built-in `process.loadEnvFile` / `--env-file-if-exists`.
- **Dates are `"YYYY-MM-DD"` strings** in every function, never `Date` objects, so a time zone can never shift a workout to another day.
- **`weight_kg` is read as a JavaScript number** (Drizzle `numeric` with `mode: "number"`), `null` for bodyweight.
- **`createExercise` on an archived name unarchives it.** The plan only says "reuse existing on case-insensitive match". Returning a still-hidden exercise would let it be added to a workout while staying invisible in the picker, so asking for it again brings it back.
- **`deleteExercise` was added** although the task list names only create, rename, archive and unarchive. The required test "a used exercise cannot be deleted" needs it, and the data-model rules imply an unused exercise (for example a typo) can be deleted. It throws `ExerciseInUseError` for a used one.
- **`searchExercises` orders prefix matches first, then alphabetically.** "Then most recently used" is part of the Phase 3 picker and is left for that phase.
- **Query functions validate their input** with the Zod schemas (`createExercise`, `renameExercise`, `addSet`, `updateSet`), so a bad value fails with a readable message before it reaches the database. The database constraints are tested separately with direct inserts.
- **Limits not in the plan:** exercise names at most 100 characters, reps at most 9999, weight at most 9999.99 kg (the limit of `NUMERIC(6,2)`).
- **Positions and set numbers stay gapless.** `removeWorkoutExercise` closes the gap in `position`; `deleteSet` renumbers one row at a time, lowest first, because a single `UPDATE` could trip the unique `(workout_exercise_id, set_number)` constraint part-way.
- **`bestSet`** = highest estimated 1RM, then most reps; among sets without weight, most reps; the earliest set wins a tie.
- **`setVolume` of a set without weight is 0**; `estimatedOneRepMax` of it is `null`.
- **Unit tests use their own database, `workout_tracker_test`.** `tests/unit/helpers/global-setup.ts` drops and recreates it on every run and applies all migrations, which is also the test that migrations apply cleanly to an empty database. Development data in `workout_tracker` is never touched. The tests refuse to run if `DATABASE_URL` does not point at `localhost`. Test files run one at a time because they share that database.
- **CI is unchanged.** The unit tests create their own database inside the existing Postgres service. CI does not run `db:migrate` on `workout_tracker` yet, because nothing reads it until E2E tests need data (Phase 2 or 3 must add that step).

## Tests added

104 unit tests in `tests/unit/` (103 new):

- `exercises.test.ts` — create (trim, case-insensitive reuse, unarchive), search (matching, order, limit, `%`/`_`), rename (including the duplicate-name error), archive keeps history, a used exercise cannot be deleted.
- `workouts.test.ts` — create if missing returns the existing one, duplicate date rejected by the database, get by date with ordered exercises and sets, notes, delete cascades to exercises and sets, summaries (sets, reps, volume, bodyweight, paging).
- `workout-exercises.test.ts` — add (order, no duplicates), remove (sets gone, gap closed), reorder (and invalid orders).
- `sets.test.ts` — add, update, delete with renumbering, last session's sets, and the database constraints (zero or negative reps, negative weight, set number 0, duplicate set number).
- `metrics.test.ts` — all four metric functions, including sets with no weight.
- `validation.test.ts` — the Zod schemas.

E2E: none new; the Phase 0 smoke test still passes.

## How to run and verify

```bash
docker compose up -d
cp .env.example .env.local   # only if .env.local does not exist yet
npm run db:migrate           # creates the four tables in workout_tracker
npm run db:seed              # optional sample data
npm run check
```

Verified locally: `npm run check` passes (lint, typecheck, 104 unit tests, 1 E2E test). `npm run db:migrate` applied to the empty local database and is a no-op when run again. `npm run db:seed` added 3 workouts and does nothing on a second run.

To look at the data: `docker compose exec postgres psql -U postgres -d workout_tracker -c "select * from exercise"`.

## Known gaps

- **CI has not run with these changes**; it runs when Adam pushes.
- Nothing in the app calls the query functions yet (no UI in this phase), and they do not check for a signed-in user. Phase 2 adds `requireUser()` to the Server Actions and data-loading functions that call them.
- `addSet` and `addExerciseToWorkout` compute the next number with `max + 1`. Two truly simultaneous calls could collide; the unique constraint then rejects one of them instead of storing bad data. Acceptable for one user.
- The seed is small. The three-month seed for charts is Phase 5.
- `npm install` prints a notice that the install scripts of `esbuild` (a dependency of drizzle-kit and tsx) and `fsevents` were not run. Both tools work without them; nothing was approved.
